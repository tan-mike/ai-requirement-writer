# Design Spec: Agentic Memory & Project Evolution

**Date:** 2026-06-01
**Status:** Approved
**Topic:** Transitioning from static requirement generation to an agentic, evolving project knowledge base.

## 1. Executive Summary
The goal is to evolve the current "Stateless Requirement Generator" into an "Agentic AI Architect" that manages projects as living knowledge bases. This system will allow projects to grow over time, supporting new feature requests and enhancements while maintaining strict consistency with existing documentation. It employs project-constrained memory, semantic retrieval (RAG), and a graph-based orchestration pattern inspired by LangGraph.

## 2. Problem Statement
*   **Static Silos:** Projects are currently limited to one set of BRD/Stories/Spec.
*   **Context Fragmentation:** New requirements don't "know" about existing ones, leading to contradictions.
*   **Stateless Orchestration:** Laravel Jobs follow a rigid linear path, making recursive refinement or complex state transitions difficult.
*   **Token Overhead:** As project history grows, injecting all past context into prompts becomes cost-prohibitive and exceeds context windows.

## 3. Proposed Architecture

### 3.1. Project Knowledge Base (PKB)
A project is no longer defined by a single file, but by a collection of **Knowledge Modules**.
*   **Modules:** Atomic units of approved project state (e.g., "User Authentication Flow", "Payment Gateway Integration").
*   **Enhancements:** New feature requests are treated as "Diffs" against these modules.

### 3.2. Memory Management (The MemoryGovernor)
A new service layer to handle project-constrained memory:
*   **Semantic Retrieval (Project-Internal RAG):** For a new feature request, only retrieve modules semantically related to the task.
*   **Incremental Synthesis:** Agents generate updates that "merge" into the PKB rather than rewriting the entire project.
*   **Distillation:** Background processes summarize old feature sets into "Condensed Context" to save tokens while preserving "Architectural Intent."

### 3.3. State-Graph Orchestration
Moving from linear Jobs to a **State Machine** pattern:
*   **Nodes:** Retrieval, Drafting, Multi-Persona Critique, Human Review, Memory Commit.
*   **Conditional Edges:** Logic-based transitions (e.g., "If Critique Score < 80% -> Retry Drafting").
*   **Persistence:** The graph state is persisted in the database, allowing for "pausable" long-running processes (Human-in-the-Loop).

## 4. Data Schema Changes

### 4.1. `project_knowledge_modules`
*   `id` (UUID)
*   `project_id` (FK)
*   `type` (Enum: feature, architecture, constraint, standard)
*   `title` (String)
*   `content` (Markdown/Text)
*   `embedding` (Vector - if using Vector DB, or JSON representation)
*   `status` (Enum: active, superseded, archived)

### 4.2. `requirement_drafts` (Modified)
*   Add `is_enhancement` (Boolean)
*   Add `target_module_ids` (JSON - list of modules this draft intends to modify/reference)
*   Add `change_impact_summary` (Text - generated by agent during review)

### 4.3. `project_state_graph` (New)
*   `project_id` (FK)
*   `current_node` (String)
*   `context_data` (JSON - the "Blackboard" state)
*   `is_paused` (Boolean)

## 5. Success Criteria
1.  **Continuity:** New requirements for existing projects are 100% consistent with previously approved modules.
2.  **Efficiency:** Token usage per generation remains relatively flat even as the total project documentation grows (via RAG and Distillation).
3.  **Flexibility:** Adding a new "Expert Reviewer" or a "Human Approval" step requires adding a graph node, not refactoring the entire Job chain.

## 6. Implementation Strategy
*   **Phase 1:** Implement `project_knowledge_modules` and basic RAG retrieval within `GeminiGenerationService`.
*   **Phase 2:** Refactor `ProcessCritiqueJob` into a "Graph Node" pattern.
*   **Phase 3:** Implement "Memory Commit" logic to transform approved drafts into new Knowledge Modules.
